# WASTE on NVIDIA GB10

This fork is the public home for the Acer Veriton GN100 / NVIDIA GB10
experiments.  It has two goals that are deliberately kept separate:

1. maintain a usable, reproducible Spark-oriented build even when a change is
   too hardware-specific or too experimental for upstream; and
2. turn generally useful pieces into small pull requests against current
   [`sqliteai/waste`](https://github.com/sqliteai/waste).

The test machine is an Acer Veriton GN100 with 128 GiB of unified LPDDR5X and
an internal 4 TB NVMe drive.  Kimi K3 is a 982 GiB WASTE container on that
internal drive.  The measured work does not add a CUDA inference backend;
it improves the existing Linux ARM64 CPU and direct-storage path.

## Repository layout

| Ref | Purpose | History policy |
| --- | --- | --- |
| `main` | Clean mirror of the latest upstream release tested here | Fast-forward from upstream; no Spark patches |
| `spark/integration` | Supported combination of the current upstream engine and accepted GN100 changes | Rebuilt deliberately when upstream changes invalidate an old design |
| `archive/sprint-5-measured` | Exact source used for the completed first five development sprints | Immutable; tagged `gn100-sprint5-results-2026-08-01` |
| `pr/*` | One generic change per proposed upstream pull request | Rebased independently; no campaign data or unrelated cleanup |

Never rebase or amend a measured archive.  A newer integration branch may
supersede its implementation, but not its evidence.

## Current measured state

The rows below are one-token K3 checks with the same deterministic prompt,
eight engine threads, direct I/O, an 86,583,021,568-byte budget, and CPU set
`5-9,15-19`.  End-to-end wall time includes model opening and prompt prefill;
the reported token time is WASTE's decode line.  The current-upstream rows are
single-run qualification points, not a replacement for a balanced campaign.

### Raw-mode bridge to Sprint 5

The completed Sprint 5 factorial used `--raw`, so this is the honest direct
bridge.  Both rows produced the same stdout SHA-256,
`bb9af6089119e3cd934e7dba08807efff93bbdb591e1b58706eece73c17f6d5b`.

| Engine | Decode | Process wall | Demand cache |
| --- | ---: | ---: | ---: |
| Upstream `c7cb640`, readers 2/depth 2, lookahead 0, PM QoS | **2.81 s, 0.36 tok/s** | **66.33 s** | 695 hit / 777 miss |
| Archived Sprint 5, whole-expert/io_uring QD4 + PM QoS | 3.20 s, 0.31 tok/s | 80.95 s | 696 hit / 776 miss |

The latest-upstream bridge is about 12% faster in decode and 18% faster
end-to-end than the accepted Sprint 5 mean.  This does not prove that
whole-expert ownership cannot add another gain.  It does mean the old
`io_uring`/whole stack must prove an incremental benefit over the new reader;
it should not be restored merely because it won against the older base.

### Current-upstream control pilot

| --- | ---: | ---: | ---: |

Two reader threads account for the large upstream gain.  Depth 4 did not
improve process wall time.  In this pilot, top-6 lookahead performed about
0.98 GB of additional filesystem input without improving time.  The PM QoS
row retained identical output and demand traffic while improving decode by
about 18% and wall time by about 19%.  Its endpoint was 67.4 C versus 64.1 C
for the matched no-Q0 configuration; wall power remains unmeasured.

All pilot rows exited successfully with zero major faults and zero process
swap.  The machine-readable rows are in
[gn100/upstream-v062-pilot.csv](gn100/upstream-v062-pilot.csv).

These are GN100 measurements, not replacements for the Mac figures in the
upstream README.

The individually proposed changes have passed their native Linux ARM64 and
server suites on the GN100.  The combined integration branch adds exact
family-root reuse and request-scoped Q0 to the available-memory, ownership,
and snapshot changes.  Its exact revision and K3 acceptance evidence are
recorded with each measured release rather than inferred from branch names.

The current integration has now passed its K3 cold/divergent/repeat gate. It
retained a 256-token system/tool root in 479,053,984 accounted bytes. The two
restored requests took 249.029 and 247.828 seconds of model work versus
857.309 seconds cold: 3.44x--3.46x faster while reading 70.5%--70.7% fewer
bytes. This was one practical persistent-server sequence, so expert-cache
warming prevents assigning the full delta to prefix reuse alone. Kimi K3's
KDA-heavy recurrent state and compressed MLA state make these snapshots much
smaller than a conventional full KV cache. Restore is accepted only after a
serialize/restore/identical-logits test, and snapshot memory is reserved from
the same hard budget as the expert cache.

## What the measured archive contains

The archived branch is intentionally broader than the proposed upstream
series.  It contains:

- Linux available-memory and cgroup-aware budget guards;
- single-owner model locking and explicit CPU affinity;
- bounded expert acquisition, a Linux `io_uring` backend, and phase/layer
  tracing;
- exact in-memory state export/import;
- exact-prefix and semantic family-root server caches;
- whole-expert scheduling;
- GN100 campaign, off-CPU, PMU, thermal, and PM QoS tools.

Some of those mechanisms now overlap with upstream's read-ahead and router
lookahead.  Accepted pieces are ported by behavior and tests, not by replaying
the old commits wholesale.

## Accepted operating profile

For this single-user experimental workstation, a phase-scoped zero-microsecond
Linux PM QoS request is an acceptable opt-in.  It prevents deep CPU idle states
while its file descriptor is open and reduced routed-loop wake/barrier delay in
the matched experiment.  The request is self-cleaning when the holder exits;
it does not alter sysfs.  It may raise system-wide idle power while active, so
it is not presented as a portable default and its wall-power cost remains
unmeasured.

The integration target exposes this as an explicit Spark profile rather than
an ambient machine tweak.  The profile records whether the PM QoS request was
actually acquired and released, treats control loss as fatal, and releases
the request on every normal and error exit.

The first current-upstream qualification separated the storage predictor from
Q0 before choosing that profile:

| Current-upstream setting | Decode | Observation |
| --- | ---: | --- |
| synchronous, no lookahead | 5.76 s | storage-overlap control |
| reader 2, depth 2, no lookahead | 3.67 s | fastest non-Q0 reader setting |
| reader 2, depth 4, no lookahead | 4.19 s | more queueing did not help |
| reader 2, depth 2, lookahead 6 | 3.81 s | about 0.98 GB more filesystem input |
| reader 2, depth 2, no lookahead + Q0 | 3.00 s | 120.60 s process wall versus 149.17 s for matched no-Q0 |

The matched Q0 and no-Q0 runs retained identical stdout and expert traffic
(422 hits, 1050 misses). Q0's endpoint temperature was 67.4 C versus 64.1 C
without Q0. These are useful qualification datapoints, not a stable estimate:
the pair has not yet been repeated in balanced order, endpoint temperature is
not an energy measurement, and wall power remains unmeasured.

The integration implements that narrow result as
`--performance-profile spark-q0`: eight threads, LFRU, verified effective
direct I/O, stable arithmetic, `WASTE_IO_THREADS=2`, `WASTE_IO_DEPTH=2`, and
`WASTE_LOOKAHEAD=0`, with `WASTE_MLOCK=0` and `WASTE_PURGEABLE=0`. Undeclared
ambient engine/debug `WASTE_*` selectors are rejected so the profile cannot
silently describe a different experiment. The default remains unchanged. The
profile requires the
request-scoped root holder documented in [SERVE.md](SERVE.md); missing or lost
control is fatal rather than a silent fallback. Health and every completed
response record the requested, acquired, released, expired, and hold-time
state.

This current base does not expose typed CPU affinity, whole-expert scheduling,
or the archived `io_uring` backend. The profile makes no claim to contain
them. Direct-I/O fallback is observable and fails strict startup. Sprint 7
adds an ABI-preserving effective-reader query, so the strict profile now also
refuses a thread-creation or depth fallback instead of reporting only its
requested environment. With prefix caching
enabled, one lease wraps both `PrefixCache.prepare()` (restore or cold-miss
prefill) and `engine.generate()`. Acquisition remains ahead of streaming
headers, and the server regression suite asserts those boundaries explicitly.

## Reproducing a qualification run

Use a converted K3 container on local NVMe.  Record the exact source commit,
binary and manifest hashes, budget, environment variables, CPU set, start/end
temperature, memory pressure, exit status, WASTE timing line, and GNU `time -v`
output.  At minimum, compare these current-upstream controls from a fresh
process:

```sh
# Upstream synchronous control
WASTE_IO_THREADS=0 WASTE_LOOKAHEAD=0 ./waste run MODEL PROMPT \
  -n 1 --temp 0 --seed 1 --threads 8 --budget 86583021568

# Upstream read-ahead without speculative router lookahead
WASTE_IO_THREADS=2 WASTE_IO_DEPTH=2 WASTE_LOOKAHEAD=0 ./waste run MODEL PROMPT \
  -n 1 --temp 0 --seed 1 --threads 8 --budget 86583021568

# Current upstream defaults
WASTE_IO_THREADS=2 WASTE_IO_DEPTH=2 WASTE_LOOKAHEAD=6 ./waste run MODEL PROMPT \
  -n 1 --temp 0 --seed 1 --threads 8 --budget 86583021568
```

Run conditions in balanced or alternating order for claims based on more than
one sample.  A one-off run is a qualification datapoint, not a stable speed
estimate.  Reject a performance row if it swaps, incurs major faults, violates
the temperature gate, changes output, changes routed experts, or silently
falls back from the backend being evaluated.

For the request-scoped server profile, use the holder command in
[SERVE.md](SERVE.md). Its status/event files are private (`0600`), its child is
an allowlisted unprivileged account, and its maximum hold is bounded. The
holder never writes sysfs or gives the privileged device descriptor to the
server. Status/event persistence is deferred until after descriptor release;
its timestamps retain boundary time and delivery time, and its transition
counters are independent of telemetry success. Because streaming callbacks
currently write to clients synchronously,
a slow client can extend the lease; do not remove the maximum-hold guard. The
example retains measured CPU set `5-9,15-19` through external `taskset`; the
profile does not yet set or verify affinity, so record it independently.

## Sprint 7 software package

Sprint 7 implements the first two items without a larger service framework:

1. `waste_get_reader_config` reports effective read-ahead threads and depth
   without changing the existing `waste_stats` layout. CLI JSON/human output,
   server responses, and the strict profile expose it; `spark-q0` refuses a
   mismatch.
2. `--conversation-head` retains one exact mutable checkpoint in addition to
   the stable family root. The root and head negotiate the same precharged
   cache reservation, and a head can never evict its root.
3. `tools/spark_serve.sh` is the complete personal-workstation launcher: fixed
   measured CPU set and budget, request-scoped Q0, effective-profile gates,
   and a two-GiB/two-entry root-plus-head cache. It does not install a daemon,
   container, UI, or system-wide configuration.
4. A balanced 16-token campaign compares current upstream defaults, the Spark
   reader without Q0, and the complete Spark Q0 profile; a sustained 64-token
   row checks that a short-run win survives longer decode. Results and exact
   artifacts are attached to the measured Sprint 7 release.

### Balanced decode result

The three-block campaign rotated the current-base default reader condition,
the selected two-reader/depth-two/no-lookahead condition without Q0, and the
same Spark condition with Q0. Every run used the same integration binary based
on upstream `c7cb640`, deterministic Italy prompt, 86,583,021,568-byte budget,
eight threads, direct I/O, and CPUs `5-9,15-19`.

| Condition (three runs) | Median decode | Range | Median process wall |
| --- | ---: | ---: | ---: |
| Current-base defaults (lookahead 6) | 58.89 s, 0.27 tok/s | 58.12–59.93 s | 174.87 s |
| Spark reader, no Q0 | 59.89 s, 0.27 tok/s | 59.72–60.25 s | 175.08 s |
| Spark reader + Q0 | **46.99 s, 0.34 tok/s** | **46.86–47.63 s** | **137.58 s** |

Q0 reduced median decode latency by 21.5% and raised throughput by 27.5%
against its matched no-Q0 control; median process wall fell 21.4%. All nine
runs produced the same stdout SHA-256. The two Spark conditions also retained
identical routed-expert totals within every run. All rows had zero swaps. The
first block recorded 1–8 process major faults; every row in blocks two and
three recorded zero, and excluding block one leaves the same practical result.

A detailed-prompt sustained check generated all 64 requested tokens in 189.44
seconds, again 0.34 tok/s, with zero major faults and zero swaps. The original
Italy-prompt “64” pilot stopped naturally after 16 tokens and is retained in
the raw archive but excluded from the sustained claim. Late-campaign onboard
telemetry ranged from 53–60 C; its `power.draw` field is not wall power and is
not used as an energy claim.

This result matches the older 0.32–0.34 tok/s Mac-era comparison that motivated
the project. It does **not** match the current upstream README's 0.45–0.62
tok/s Mac range: 0.34 is about 24% below that range's lower bound. The campaign
therefore establishes a repeatable Spark software gain and an honest current
comparison, not parity with the fastest currently published Mac numbers.

Compact rows are in
[gn100/sprint7-baseline.csv](gn100/sprint7-baseline.csv); full commands,
host/memory snapshots, Q0 records, timing output, and checksums are attached to
the Sprint 7 release.

### Exact-code launcher and conversation-head qualification

The detached public code commit `875da0e065f45065bce51ced34e4a5e05adb33df`
built natively on the GN100, passed 28 native checks with 13 explicit
model/reference skips, and passed all 264 server checks. The thin launcher then
opened the real K3 container with the fixed 86,583,021,568-byte budget, CPUs
`5-9,15-19`, request-scoped Q0, and a two-GiB/two-entry cache. Startup reported
effective direct I/O and exactly two readers at depth two.

The first 146-token prompt was a cache miss and admitted both a stable root and
a 128-token conversation head. The second, longer 183-token full-history
prompt restored that exact head and replayed 55 tokens. After both requests the
cache retained exactly one root and one head in 940,407,872 accounted bytes,
with no rejects, evictions, restore failures, snapshot failures, or allocation
failures. Both requests acquired and released Q0; the holder recorded two
opens, two closes, two completed leases, and no expiration, protocol, device,
or telemetry error.

Cold model work was 349.038 seconds and 635,004,018,688 cumulative bytes read.
The larger next turn took 133.852 seconds and added 254,004,088,832 bytes:
2.61x faster model work and 60.0% fewer incremental bytes. As with the
family-root result, the persistent expert cache also warmed, so this is a
combined user-experience qualification rather than an isolated causal estimate
of the head alone. Synthetic real-engine acceptance is the bit-exact proof:
the next-turn output and complete post-generation state match uncached
execution byte for byte.

The functional qualification started with 122,737,549,312 bytes available and
ended with 124,756,054,016. System-wide vmstat advanced by 225 major faults,
11 swap-out pages, and reclaim scans while no swap-in occurred; the existing
swap allocation reported by `free` was unchanged. Those host-wide counters do
not invalidate the exact restore check, but they keep this two-request run out
of the clean performance campaign above.

The software acceptance suite requires exact next-turn output and complete
post-generation state bytes against uncached execution, plus altered-history
fallback, tight-budget root preservation, effective-reader mismatch refusal,
and native GN100 launch evidence.

The next research choice remains learned, confidence-gated cross-layer
prefetch versus other product-facing latency work. It should be decided only
after this release, with byte amplification measured independently of
scheduling. Wall power remains useful but does not block that decision.

Whole scheduling and deeper queueing remain out of the integration path unless
a new matched measurement reverses their current no-gain results.
